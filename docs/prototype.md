# The 3D smart-garden prototype

All data is **demonstration data**. It is deterministic and labelled "Demo data / Demo-Daten" in the UI. No hardware is connected.

## The four stages

| Stage | Visible | Interaction | Panel |
|---|---|---|---|
| 1 · Planning | Plot grid, house drawn as lines (build-in: plan → dimensions → walls), construction lines, dimension strings (8.00 / 7.00 / 3.80 / 4.50 / 28.00 / 18.00 m), dashed potential planting zones, existing trees as sketches | Orbit, zoom, hover/click a zone | Zone list → zone details (area, sun, soil, status) |
| 2 · Planting | Materials fade in; beds rise one after another; plants grow; score chips | Click a plant, bed or chip | Ranked list → plant card (name, species, score ring, reason, requirements) |
| 3 · Monitoring | One soil probe per bed and a weather station; moisture chips coloured by status | Click a probe, bed, plant or chip | Overview with a measured/estimated legend → device dashboard (moisture chart with target band, sparklines, **estimated** care index) |
| 4 · Irrigation | Supply line, valve manifold (one valve per bed), laterals, drip lines, emitters; decision chips | Weather (dry / rain expected), strategy (adaptive / fixed timer), **Run watering demo** | Water used, beds watered, over-watered / still dry, savings, per-bed decision with plain-language reason |

The selection carries across stages: bed 1 → tomato → probe 1.

## Hardware model (what is honest to claim)

- **Sensors** (matches the PPTX's planned set: soil and air moisture, temperature, irradiance, plus weather data): one capacitive soil probe per bed (soil moisture % VWC, soil temperature) and one weather station (air temperature, relative humidity, light in klx, rainfall).
- **Plant health is never measured.** `utils/health.ts` estimates a 0–100 care index from moisture against the target range and from temperature stress. It is always labelled *estimated*.
- **Irrigation:** one solenoid valve per raised bed, feeding two drip lines with 2 L/h emitters every 0.3 m. Each bed holds one species, so control is **per species** (PPTX: "Bewässerung für einzelne Pflanzenarten"). Individual plants are **not** valved individually, and the UI says so.

## Decision logic (`utils/irrigationLogic.ts`, pure)

| Condition | Action |
|---|---|
| within target | skip |
| above target | skip (watering would harm) |
| below target, rain expected (≥ 5 mm and ≥ 60 %), not critical | **defer** |
| more than 5 points below target (critical) | water to the mid-range; only to the lower limit if rain is expected |
| below target, dry forecast | water to the mid-range |

Litres = Δmoisture × root depth (0.10 m) × wetted area (3.03 m²) × 1000. Duration = litres ÷ (emitters × 2 L/h). The fixed timer gives 20 L per bed, daily, regardless.

Demo outcome (dry spell): adaptive waters **tomato (36.3 L) and basil (21.2 L) = 57.5 L**. The fixed timer uses **120 L**, over-waters lavender, kale and rosemary, and still leaves the tomato too dry. Saving: **63 L (52 %)**. With rain expected, basil waits for the rain and tomato receives only 21.2 L.

## Extending

**Add a plant / change a bed** (`data/plants.ts`): add a `GardenPlant` with `plantingZoneId`, `moistureTarget`, `layout` (rows must be **even**, because the probe sits in the bed centre) and a `model`. A new species also needs:

1. a `PlantModel` entry in `types/index.ts`;
2. a `case` in `speciesParts()` (`components/Plant.tsx`) built from `GEOMETRY` parts and materials;
3. a German entry in `DE_PLANTS` (`data/i18n.ts`).

`geometry.test.ts` will fail if the plants leave the bed or crowd the probe.

**Add a bed:** add a `PlantingZone` (`data/site.ts → PLANTING_ZONES`) with an `irrigationZoneId`. The irrigation zone, probe, routing and chips are derived automatically. Run the tests: routing guarantees non-crossing laterals for the 2 × N layout.

**Change sensor fixtures** (`data/sensors.ts`): `CURRENT_SOIL_MOISTURE` sets the "now" value per bed; histories are generated by `generateSeries` from a seed and end exactly at that value. Never use `Math.random` (`npm run validate` checks this).

**Replace the building model:** the house is parametric (`HOUSE_MAIN`, `HOUSE_WING` in `site.ts`; glazing in `House.tsx`). To use a real model, place a GLB in `public/assets/models/`, load it with drei's `useGLTF` inside `House.tsx`, and keep the `walls` group wrapper (its `scale.y` is the build-in animation). Update the footprints in `site.ts` so the overlap tests keep protecting the layout. No GLB was supplied, so none is included.

**Add a stage:**

1. Add the name to `GARDEN_STAGES` (`types/index.ts`).
2. Add a layer in `LayerProgress` / `layerTargets` / `LAYER_ORDER` (`utils/stages.ts`).
3. Add a camera preset in `STAGE_CAMERA`.
4. Add copy in both locales.
5. Add a panel component in `stages/` with a case in `GardenScene → StagePanel`.
6. Add a mapping in `selectionForStage`.

TypeScript's exhaustive `switch` statements point to every place you missed.

## Connect the recommendation framework

`data/recommendations.ts` defines `RecommendationProvider`. Today, `demoRecommendationProvider` serves the fixture. For the real framework:

```ts
const provider = createHttpRecommendationProvider("https://api.plantwiz.example");
const recs = await provider.getRecommendations(["bed-1", "bed-2"]);
const plants = applyRecommendations(PLANTS, recs);
```

Expected JSON: `{ "recommendations": [{ "plantId": "tomato", "zoneId": "bed-1", "score": 0–100, "reason": "…" }] }`. `parseRecommendationResponse` **rejects** unknown plants or zones, out-of-range scores and missing reasons instead of rendering them. To drive the scene from live results, pass the merged `plants` where `PLANTS` is read today (`plantForZone`, `RECOMMENDED_PLANTS`). Turning these into a context provider is the remaining integration step.
